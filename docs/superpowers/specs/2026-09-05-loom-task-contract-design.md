# Loom 面向任务的 DSL 完整性与结构调整方案

状态：已按用户确认落实为 v0.5 / v1alpha2 静态契约。本文保留设计依据；最终字段、角色数量、验收执行角色和版本规则以[现行主规范](../../AGENT_DSL_SPEC.md)及[字段参考](../../DSL_FIELD_REFERENCE.md)为准，运行引擎不在本轮交付范围。

配套必读：[声明依赖关系图与边界规范](2026-09-05-loom-dependency-boundaries.md)。本文与配套文档采用同一设计：task 独立定义业务，role 表达任务分工，seat 只提供可复用岗位配置；不维护 seat.tasks 反向关系。

## 1. 目标与边界

DSL 首先回答：这个 Agent 为谁解决什么问题，接收什么任务，在什么环境中，使用哪些能力和资源，遵守哪些边界，按什么过程完成工作，与谁交互，交付什么结果，并用什么标准确认任务完成。

本次交付范围为规范、Schema、静态校验、示例及迁移说明，不实现调度平台、消息中间件、完整编译器或运行时。Draw.io 图不修改，不提交或覆盖用户已有工作区修改。

## 2. 三种调整方式

| 方案 | 收益 | 代价与判断 |
|---|---|---|
| 只扩写说明，继续使用现有字段 | 无结构迁移 | 无法解决 Agent 级输入、结果、验收与交付绑定缺失，不选 |
| 新增一个 tasks 任务契约入口，复用现有组件 | 形成业务闭环，只有一个新增顶层概念 | 需要新增 Schema 和语义校验；推荐 |
| 新增 inputs/triggers/interactions/deliveries/evaluations 等多个顶层系统 | 各能力独立扩展 | 引用关系复杂，简单任务也需要大量装配；当前不选 |

## 3. 唯一事实源

| 问题 | 声明位置 |
|---|---|
| 长期业务目的 | metadata.purpose |
| 全局身份、职责和承接范围 | identity |
| 可执行的一类任务、目标、输入、结果、交互和验收 | tasks[]，本次新增 |
| 一次请求的输入、调用人、请求编号和截止时间 | 运行时请求信封，不写入静态 Agent 清单 |
| 运行状态、结果和投递回执 | 运行时记录，不回写任务定义 |
| 能力定义、依赖与所需副作用 | components、requires、effects |
| 共享能力包 | assembly；仅在需要复用分组时使用 |
| 角色及能力可见范围 | seats |
| 实际授权上界 | gate、资源访问模式和部署环境共同决定 |
| 强制业务阶段与人工审批 | workflow 组件 |
| 文件产物格式、位置和生命周期 | output 组件 |
| 质量检查定义 | review 组件；任务负责绑定检查对象与执行时机 |
| 如何启动宿主及选择默认任务 | launch |
| 定时器、HTTP 监听地址、消息订阅和凭据 | 部署绑定，不伪装成 launch 或 workflow 事件 |

## 4. tasks：一个新增顶层结构

tasks 是具名任务契约数组，存在时至少一项，任务 id 唯一。每项描述可反复执行的一类业务任务，不是一次运行实例。

| 拟定字段 | 必要性 | 含义与约束 |
|---|---|---|
| id | 必填 | 任务标识，供调用与启动入口引用 |
| objective | 必填 | 本类任务的业务目标，不替代机器验收规则 |
| components | 执行配置三选一 | 直接选择执行能力，适合不需要岗位复用的简单任务 |
| seat | 执行配置三选一 | 引用一个可复用岗位，不在任务里复制岗位配置 |
| roles | 执行配置三选一 | 多角色分工；每个角色包含 id、responsibility，并在 seat/components 中二选一 |
| workflow | 可选；需要强制交接时使用 | 引用流程定义，其角色槽位由 task 绑定；不再由流程反向引用 seat |
| inputSchema | 必填 | 整个任务接受的业务输入结构；与工具参数 Schema 独立 |
| resultSchema | 必填 | 整个任务业务结果的结构；不包含运行时状态和错误信封 |
| interaction | 必填 | 交互模式与缺失信息处理规则 |
| acceptance | 可选 | 额外业务检查绑定，每项引用 review 组件及检查对象；输入结果结构校验始终执行 |
| delivery | 必填 | 结果返回方式，本轮核心只定义 caller 返回，外部交付单独明确边界 |

inputSchema/resultSchema 复用现有内嵌 JSON Schema 校验方式，不开发第二套类型系统。运行时必须验证输入实例和结果实例，静态校验不能冒充实例校验。

interaction.mode 为 interactive 或 non_interactive；interaction.on_missing_input 为 ask 或 fail。ask 只允许 interactive。缺失信息未补齐前不调用有副作用的业务动作；用户补充后仍按原输入 Schema 校验。取消不是拒绝审批的同义词。

acceptance 每项包含 review 和 target，review 引用 review 组件 id；target 为 result 或一个 output 组件 id。检查固定在交付前执行，本轮不增加任意阶段表达式。目标为 output 时必须是任务明确声明的产物，检查执行上下文必须具备所需读取能力；多角色场景不得默认合并所有角色权限。具体验收执行上下文选择须随正式字段定义明确。review 的 error 阻断交付，warn/info 留在验收报告；检查失败不自动重跑业务写操作。

delivery 核心形态为 mode: caller，返回到发起该请求的受信会话或调用通道，不接受模型自由生成接收人。文件产物仍由 output 声明并在结果中返回受授权的产物引用；不把本地路径当作远端可访问链接。

外部发送在本轮说明为显式发布能力：通过已有 tool/bridge/resource 和 gate 完成，必须由部署适配器定义目标、鉴权、幂等和回执。没有适配器时不得宣称 webhook、PR 或消息发送已经完成。本轮不新增通用投递引擎和重试 DSL。

## 5. 触发、运行和成功的契约

外部入口经鉴权后提交 task_id、request_id 和 input；调用人及回信通道由适配器建立，不信任输入正文自报的身份和目的地。对话、API、定时器和事件订阅都可以映射到这个统一入口，但不因此宣称仓库已经实现这些接入器。

静态配置只定义任务；定时器时区、监听地址、消息消费者和重投策略由部署配置负责。部署绑定必须指向已有任务并在启动时检查 adapter 支持，不得静默忽略未知触发源。

一次运行顺序：接收并鉴权 → 校验输入 → 必要时补充输入 → 绑定席位与可选流程 → 执行授权动作 → 校验结果结构 → 运行验收 → 返回结果并记录交付状态。

运行记录分开保存 execution、evaluation、delivery 状态，避免把“程序返回”“检查通过”和“对方收到”混为一谈。统一错误至少保留稳定 code、任务及请求标识、阶段、可读原因；不返回凭据和敏感工具原始输出。

resultSchema 合法和 review 通过只能证明声明的检查成立。objective 的自然语言目标仍可能需要人工判断，不承诺自动证明任意业务目标。

## 6. assembly 与 seats 的最小化调整

保留三个不同职责：assembly 整理能力包，seats 分配角色能力，gate 约束真实动作。

允许 seat 在 groups 与 components 之间严格二选一；components 直接引用组件 id，适合单席或不复用分组的场景。只有使用 groups 引用时才要求 assembly；不自动把所有组件暴露给默认席位，不自动创建席位，不推断或扩大权限。

两种写法归一后使用同一种席位能力集合和依赖闭包。read_only 校验对直接组件和分组引用完全一致。旧配置保留原语义，groups/components 同时出现必须拒绝。

简单 task 可直接选择一个 skill，继承 Agent identity，不必建立默认 seat。seat 仅用于复用稳定岗位配置；assembly 仅用于复用能力分组。两者都不自动授予权限，也不允许省略能力选择后自动暴露所有组件。

seat 不引用 task 或 workflow；task 引用 seat，workflow 声明局部角色槽位，由 task 提供绑定。assembly 只装配 skill/tool/bridge/knowledge 能力，不承载流程、产物、验收或 gate。

## 7. workflow 与 knowledge 的定位

workflow 保留组件形态：它是有版本、可校验的流程定义，不是普通工具，也不是一次运行实例。任务引用流程并绑定角色槽位，运行时维护当前阶段。移除 workflow.seat 的反向岗位耦合和 tool.phase 的反向流程耦合：流程定义阶段需要的角色和工具，task 将角色绑定到执行配置。多角色声明仅提供分工契约，不意味着已实现调度、上下文隔离或恢复。

知识相关名称在说明中统一：resources 中的是“知识存储资源”，knowledge 组件是“知识域组件”，顶层 knowledge 是“知识生命周期”。近期不改已有字段名，不制造无必要迁移。

制度助手示例中：资源登记制度目录；知识域定义条目结构；生命周期规定候选与晋级；查询、维护和审查席位各选能力包；gate 禁止修改正式制度。普通文件读取无需凑齐三类知识声明。

## 8. 兼容与版本

文档版本为 v0.5，新 API 固定为 agent-dsl/v1alpha2；历史 v0.4/v1alpha1 独立归档和测试，不在同一解释模式下兼容两种语义。runtime.version 仍是独立的宿主版本，不能随文档版本机械修改。

旧清单可以继续做组件装配与原启动入口校验；没有 tasks 不再描述为已声明完整任务契约。新任务入口使用 launch.entries[].task，与旧 seat/seats/workflow 选择方式互斥，执行配置和 workflow 从任务解析，不重复声明。旧配置按旧契约测试；转换后的示例按新契约测试，不以放宽新规则保留旧语义。

output.publish 现有远端方式保留兼容，但不新增第二套隐式发布路径；文档明确 output 是资产契约，任务 delivery 是请求结果返回，业务外部发布是需要执行器的实际动作。

## 10. 验证与非目标

新增正反例覆盖：任务 id 与引用、无效输入/结果 Schema、交互组合冲突、验收目标不可见、review kind 不符、入口任务与席位选择冲突、seat 两种能力引用互斥、直接引用下 read_only 传递依赖检查。

保留旧正反例作为旧版本回归，并为迁移后的新语义建立独立测试；文档字段覆盖与 YAML 片段检查继续执行。对实际请求实例和结果实例采用测试用样本验证，不将其描述为已实现任务执行服务。

不新增通用调度语言、目标推理引擎、评分平台、自动补偿事务、任意表达式求值、跨席并发调度、消息可靠投递系统。运行时恢复与外部适配器是需要明确实现的后续工程，不能靠增加枚举值宣称完成。
